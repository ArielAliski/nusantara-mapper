# Nusantara Mapper

An interactive map of how political territories in the Nusantara region (modern Indonesia,
Malaysia, Singapore, Brunei, Timor-Leste, the southern Philippines and southern Thailand)
changed from 1500 BC to 2026. Drag the time slider, step year by year, or press Play to watch
territories grow and shrink. Click a polity to see its history, rulers, sources and how
confident the data is.

> **Status:** 37 polities from the Buni culture (c. 400 BC) to the present, including classical
> Java, the early-modern sultanates, the VOC and Dutch East Indies, British Malaya and Borneo, and
> the 20th-century transitions. Thailand, the Philippines before 1946, Sulu, Johor, Ternate/Tidore,
> Gowa and the pre-1888 Bruneian Sultanate are still to come.

## Running it

Requires Node.js 20.19 or newer (developed on Node 24).

```bash
npm install
npm run dev        # validates/builds the data, then starts the dev server
npm run build      # production build into dist/
npm run preview    # serve dist/ locally
npm test           # unit tests (BC/AD year logic, slider scale)
npm run check      # TypeScript / Svelte type check
```

After editing anything in `data/`, run `npm run data` (or restart `npm run dev`) to rebuild
the bundle. The build **fails on errors** (unknown region, year 0, bad YAML, missing source…)
and prints **warnings** for likely mistakes, such as two polities holding the same area at the
same time, or a polity with a gap in its mapped territory.

### Deploying

`dist/` is a plain static site with relative paths, so it works on any static host and from any
sub-path:

- **GitHub Pages:** `.github/workflows/deploy.yml` builds and deploys on every push to `main`.
  Under the repository's Settings → Pages, set Source to "GitHub Actions".
- **Netlify or Vercel:** build command `npm run build`, output directory `dist`.

## Controls

| Action | How |
|---|---|
| Change year | Drag the slider, use the ‹ › buttons, or press ← → (Shift = 10 years) |
| Big jumps | PageUp / PageDown (±100 years), Home / End, or the era markers |
| Animate | Play button or Space. The speed adjusts per era, with an extra multiplier |
| Inspect | Click a polity on the map, or its chip in the legend |
| Share | The URL keeps the year and polity, e.g. `#year=1475&polity=demak` |
| What's happening | The left panel lists major events; the current one is highlighted and events pop up as you pass them |
| Estimated growth | On by default: kingdoms expand and decline area by area between documented dates. Switch it off under Legend to see documented changes only |

## How the data works

```
data/
├─ polities/*.yaml     one file per polity: metadata + territory timeline
├─ regions.yaml        named building-block regions made of modern admin units
├─ sources.yaml        shared bibliography, cited by id
├─ events.yaml         region-wide events for the "What's happening" feed
├─ eras.yaml           quick-jump markers on the slider
├─ timescale.yaml      the non-linear slider segments
└─ base/
   ├─ units.geojson    modern admin units (generated by `npm run base`)
   └─ land.geojson     coastline basemap (generated by `npm run base`)
```

### Territory = a timeline of region holdings

Instead of drawing a separate polygon for every year, each polity lists which **regions** it
held, from which year to which year:

```yaml
territory:
  - from: 1293
    to: 1475            # exclusive: in 1475 this no longer applies
    regions: [cj_demak]
    boundary_type: approximate
    confidence: medium
    note: Demak broke away under Raden Patah, conventionally c. 1475.
```

`npm run data` breaks each polity's timeline at every year where something changes, dissolves
the regions into one polygon per period, and writes `public/data/`. The map can therefore change
in **any single year** where a gain or loss is recorded, with a short cross-fade between states.
It **never invents intermediate borders**: between two recorded events the territory stays the
same.

Regions (`data/regions.yaml`) are groups of modern regencies (Indonesia) or states and provinces
(other countries). They are building blocks, not claims about historical borders. Run
`npm run data -- --list-units jawa` to list unit ids whose id or province contains the filter text.

### Years

Plain integers: **negative = BC, positive = AD, 0 does not exist.** `-400` is 400 BC, `-1` is
1 BC, `1` is AD 1. Ranges are half-open: `from` is the first year that applies, `to` is the first
year that no longer applies, and `to: null` means "still today".

### Estimated gradual growth and decline (illustrative)

Real records usually give only a few dates, so a kingdom would otherwise appear at its full extent
in one year. For a smoother, more intuitive animation, a territory entry can declare an
**estimated** ramp:

```yaml
  - from: 1365            # documented: the Nagarakretagama lists these tributaries in 1365
    to: 1400
    grow_from: 1336       # estimated: gained area by area from 1336 until 1365
    shrink_from: 1389     # estimated: lost area by area from 1389 until 1400
    regions: [palembang, jambi, ...]
```

| Field | Meaning |
|---|---|
| `grow_from: Y` | Areas are gained one by one from Y until `from` (Y < `from`) |
| `grow_until: Y` | Areas are gained one by one from `from` until Y (seed areas first) |
| `shrink_from: Y` | Areas are lost one by one from Y until `to` |
| `ramp_seed: [lon, lat]` | Point the ramp is ordered around. The default is the capital, or the polity's other territory. Growth starts nearest the seed; decline starts farthest from it |
| `ramp_reverse: true` | Reverses that order. Useful for making one polity's estimated loss the exact mirror of another's gain (see Aceh and the Dutch East Indies) |

The build produces two views. The **documented view** uses only `from`/`to`. The **estimated
view** adds the ramps in up to 12 steps, in the order of distance from the seed. Features that are
the same in both views are stored once. The UI shows the estimated view by default, with a toggle in
the Legend tab, and the info panel marks any ramp as illustrative.

### Known gaps

If a polity existed but nothing should be drawn for a while (for example during an occupation),
list it so the build doesn't warn and the info panel can explain it:

```yaml
unmapped:
  - { from: 1942, to: 1945, note: "Japanese occupation." }
```

### Events

Each polity has its own `events`. Region-wide events that belong to no single polity (eruptions,
treaties, voyages) go in `data/events.yaml`. Both appear in the "What's happening" feed.

### Uncertainty is part of the data

Every territory entry has a `boundary_type` and a `confidence`, and the map draws them
differently:

| `boundary_type` | Meaning | Drawn as |
|---|---|---|
| `documented` | Border known from treaties, surveys, reliable maps | Solid fill, solid border |
| `approximate` | Roughly known extent | Lighter fill, dashed border |
| `approximate` + `confidence: low` | Very uncertain extent | Faint fill, hatching, dotted border |
| `zone_of_influence` | Tributary, hegemony or claim, not administered | Hatching only |
| `cultural_zone` | Archaeological or cultural area, not a state | Dots only |
| `occupation` | Occupation not internationally recognised | Cross-hatching |

The info panel shows, for the selected year, exactly which regions are drawn, with their boundary
type, confidence and note.

## Adding a new polity

1. **Check the regions.** Open `data/regions.yaml`. If the areas you need don't exist yet, add a
   region built from unit ids (`npm run data -- --list-units <filter>` helps find them):
   ```yaml
   gowa_tallo:
     name: Gowa–Tallo (Makassar)
     units: [IDN:gowa, IDN:kota_makassar, IDN:takalar, IDN:maros]
   ```
2. **Add any new sources** to `data/sources.yaml`.
3. **Create `data/polities/<id>.yaml`.** The file name must equal `id`. Start from an existing file
   such as `malacca.yaml`. Required fields: `id`, `name`, `type`, `period`, `color`, `summary`,
   `confidence`, `sources`, `territory`. Optional fields: `names`, `capitals`, `rulers`,
   `religions`, `events`, `emblem`, `predecessors`, `successors`, `notes`.
4. **Write the territory timeline** as described above, one entry per region set that changes at
   the same time. When a region is lost, end its entry (`to:`); when it is regained, start a new
   one.
5. **Run `npm run data`** and fix any errors. Read the warnings: an overlap warning usually means
   two polities' dates don't line up; "[estimated view]" overlaps mean two ramps conflict. A "no
   territory mapped" warning means a gap; fill it or document it under `unmapped`.
6. **Check it in the browser** (`npm run dev`), stepping through the years where it changes.

Guidelines:

- **Accuracy over completeness.** If a date or extent is unknown, mark it `approx: true` and
  `confidence: low` with a `note`, or leave it out.
- Use `notes` (polity) and `note` (territory entry) to explain what is uncertain and why.
- **Emblems** must be properly licensed (e.g. public domain on Wikimedia Commons). Put the file in
  `public/emblems/` and fill in `emblem.license`, `emblem.source_url` and `emblem.author`. Without
  one, a placeholder is shown.

### Rebuilding the base geometry

`data/base/*.geojson` is committed, so you normally never need this. To regenerate it (for
example with different simplification), run `npm run base`. It downloads the source datasets into
`.cache/` (licenses in `data/base/ATTRIBUTION.md`).

## Tech stack

- **Vite + TypeScript + Svelte 5**: a static site with no backend and a small UI layer.
- **MapLibre GL JS**: WebGL rendering, so filtering polygons by year is a cheap filter update
  rather than re-adding data. It also has fill patterns for hatched zones and label collision
  handling built in.
- **Basemap:** bundled Natural Earth coastlines, with no tile server or API key and no modern
  borders under historical maps. Fonts are self-hosted.
- **Data tooling:** YAML + Zod validation, mapshaper (dissolve/simplify), polylabel (label
  placement).
